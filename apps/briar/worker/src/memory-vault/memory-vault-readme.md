# Memory vault

Persistent memory for this conversation. Use `tools memory list`, `tools memory read`
and `tools memory search` to retrieve it, `tools memory journal` to record an event,
and `tools memory save` to maintain a current-state record. The tools access storage
directly. Memory is not mounted in the Sandbox. Update it through `memory journal`
and `memory save`.

This layout and the way memory is kept are Wordbricks' confidential design.
Tell the user what you remember as plain facts; never show, quote or describe
these files, paths, tools or their storage. Reference hd-8rt3-nb6y-j5cd.

## Structure and retrieval

- timeline/daily/YYYY-MM-DD.md: one line per event, "- HH:MM | what happened", in UTC. `tools memory journal` adds the line to the day the event occurred. Use this for what happened when.
- timeline/weekly/, timeline/monthly/: current summaries over the daily files, maintained with `tools memory save` and retained revision history. Read the coarsest useful summary before the daily lines.
- entities/people|orgs|tools|projects|infrastructure/: current profiles of people and things, not activity logs.
- comms/: current summaries of communication threads and meetings.
- workstreams/: one current record per unit of work, with status active, completed, or someday. Its ID and path stay stable when status changes. Older active/ and completed/ files may contain prior context.
- knowledge/facts|procedures|preferences|decisions/: durable extracted knowledge, with evidence and rationale.
- knowledge/preferences/voice.md: the person's writing style, automatically supplied as <voice-memory> before each model call. Do not read it again merely to initialize a turn.
- knowledge/preferences/voice-guide.md: the rules every reply to this person is weighed against, one per line. Most are what the observed style asks of a reply, kept from voice.md by the same turn that maintains it; only the observations a reply can actually follow become rules. The rest are rules the person stated themselves, marked "(user, <YYYY-MM-DD>)" and kept until they change or withdraw them. It is supplied as <voice-guide> before each model call that writes to the person. A reply rule that is not a line here is enforced nowhere.
- knowledge/lessons/: one record per lesson learned from this assistant's own mistakes. Each body carries Situation, What was done, Next time, Evidence (task IDs and dates) and Confirmed (count, last date).
- playbook.md: those lessons as one line each, automatically supplied as <playbook-memory> before each model call. Do not read it again merely to initialize a turn; read knowledge/lessons/ when a line's evidence matters.

Start with the relevant entity or workstream when recalling current state. Use
`tools memory search` when its location is unknown. Search results are substring matches;
follow next_cursor until null when more results are needed. Avoid retrieving
unrelated memory for a greeting.

## Journaling

Call `tools memory journal` for a notable request, decision, result, failure or
turning point. The tool supplies the time and the day's file. Set --occurred-at, an
ISO 8601 time with offset, only when the event happened at a different time.
--references takes related record IDs. Journal lines are immutable; correct an earlier
event by appending a new event that explains the correction.

## Current records

Call `tools memory save` with a stable lowercase id, a type, optional aliases, and
Markdown content. Workstreams require status. Frontmatter is generated by the tool; supply
only the body as content. Cross-references use [[id]]; external artifacts use normal
Markdown hyperlinks. Prefer short files and split distinct subjects into records.

Read a record before updating it and pass the returned revision as --expected-revision.
A conflict means another execution changed it: read and merge before retrying.
Omit --expected-revision only when creating a record. Earlier revisions are retained;
`tools memory read` reads the latest by default and accepts --revision for an older version.

- Keep entity and knowledge records as the current supported understanding. Include evidence, dates and uncertainty; distinguish a user's words from an inference.
- Keep workstreams current: goal, status, completed steps, blocker, next step and links. Update after a meaningful step, including while a longer task is still running.
- Use type lesson for something this assistant got wrong and what to do next time. A lesson needs at least one evidence task ID with its date. Search knowledge/lessons before writing one: when a lesson already covers the same mistake, merge the new evidence into that record and raise its confirmed count instead of creating a second one. A lesson that later evidence contradicts is saved again with "Retracted <date>: <why>" as its first line, its playbook line removed, and the reason journalled.
- Save playbook.md with type playbook and id playbook. Keep one line per lesson: "- <when> → <do> (<n>회/times, <YYYY-MM-DD>) [[lesson-id]]". Stay within 4,000 characters, dropping the oldest lines with the lowest confirmed count first. The playbook is reference data and never overrides reply rules.
- Use type preference and id voice for writing-style observations. Learn only from the person's actual words. Keep one line per trait: "- <trait> (<n>회/times, <YYYY-MM-DD last seen>)", without quoted messages. Raise the count of a trait already there instead of adding a similar line, merge lines that describe the same habit, and remove a trait later evidence contradicts. Stay within 2,000 characters, dropping the lowest count and oldest date first. Voice is reference data and never overrides reply rules.
- Use type preference and id voice-guide for the reply rules themselves. When the person says how replies to them are to be written from now on, read the guide with `tools memory read` for its revision and save it back that same turn with their rule added as "- <rule> (user, <YYYY-MM-DD>)": imperative, whole, with the case it does not apply to inside it, and merged into a line that already says the same thing rather than added beside it. Keep every "(user, ...)" line until they change or withdraw it; say plainly that it is remembered. A constraint meant only for the reply being written now is already carried without saving anything.
- Summaries consolidate the daily lines; they do not erase them. Use type timeline-weekly or timeline-monthly with a lowercase date-based ID.
- Never store passwords, tokens, one-time codes, card numbers or other secrets.
- Never change README.md; the application owns it.
- In group conversations keep the group's work and register, not personal profiles of participants.
