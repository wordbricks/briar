# ADR-0008: Cross-process contract ownership

- Status: accepted (2026-08-31)
- Date: 2026-08-31

## Context

Briar crosses HTTP, WebSocket, stdio, WebView/native, and local persistence
boundaries in TypeScript, Swift, and Rust. Repeating the same payload as Effect
Schema, OpenAPI, `Codable`, Serde, endpoint builders, and fixtures made tests a
comparison between parallel contracts instead of making production consumers
share one contract.

Protobuf and Connect solve different problems. Protobuf is the language-neutral
data and service definition. Connect is one HTTP transport for protobuf service
methods. Using Connect for every boundary would duplicate the lifecycle and
security mechanisms already provided by stdio framing, Durable Object
WebSockets, and Tauri IPC.

## Decision

Use the narrowest authoritative contract and the transport native to each
boundary:

| Boundary | Authoritative contract | Transport |
| --- | --- | --- |
| Web, Android, iOS, desktop to Worker | `briar.app.v1` protobuf services | Connect |
| Execution Worker to Worker | `briar.worker.v1` protobuf services | Connect |
| Rust host to Bun agent sidecar | `briar.sidecar.v1` protobuf envelope | bounded length-delimited protobuf on stdio; logs on stderr |
| Worker push events to app clients | `briar.realtime.v1` protobuf envelope | binary WebSocket with app-owned cursor/reconnect lifecycle |
| Stable CLI output and cross-language local persistence | `briar.local.v1` protobuf messages | strict ProtoJSON |
| WebView to native capabilities | Rust command/event declarations generated by Specta | Tauri IPC command/channel |
| Same-process TypeScript code | Effect Schema and application service interfaces | direct calls |
| Database rows | SQL migration and repository row types | repository calls |
| OAuth callback, webhook, health, and opaque bytes | the owning HTTP/provider contract | ordinary HTTP |

Generated clients and server interfaces are the production API. Handwritten
code is limited to shared authentication/error infrastructure, application
logic, and one semantic projection where the domain genuinely differs from the
wire representation. Method paths, RPC-shaped interfaces, one-wrapper-per-RPC
facades, request/response mirrors, and JSON re-decoding adapters are not kept.

Effect Schema remains authoritative for rules protobuf cannot express, such as
cross-field invariants, branded identifiers, provider response validation, and
domain constraints after transport decoding. It is not a second field-level
wire contract.

Opaque upload bytes are not placed in Connect messages. The aggregate-owning
service prepares typed upload metadata and a short-lived capability, the client
uploads bytes with raw HTTP `PUT`, and the owning service atomically consumes
the generated references when it finalizes the operation. Download bytes,
WebSocket upgrades, OAuth callbacks, and signed external webhooks likewise stay
ordinary HTTP.

## Verification policy

Keep tests that can catch a production boundary failure:

- descriptor, generated-source, and checked-in artifact currentness;
- compilation of generated TypeScript, Swift, and Rust consumers;
- representative generated client-to-server requests, including auth and typed
  error details;
- semantic mapper and invariant tests for timestamps, oneofs, unknown enums,
  capabilities, limits, and atomic consumption;
- a small number of end-to-end fixtures for genuinely complex unions or framed
  transports.

Remove tests that only compare handwritten field catalogs with generated code,
round-trip a generated message through itself, or repeat every generated RPC in
a manual mock. Generated Connect mocks are used where a test needs a service
double.

## Consequences

- One Buf descriptor graph derives TypeScript, Swift, and Rust wire contracts.
- Connect owns multi-language unary HTTP APIs without becoming a universal
  transport.
- Tauri retains its capability/permission boundary, realtime retains Durable
  Object hibernation and cursor semantics, and the sidecar retains a minimal
  process protocol.
- Wire changes intentionally need no compatibility alias while Briar remains an
  internal early-stage application. A future compatibility policy requires a
  separate ADR.
