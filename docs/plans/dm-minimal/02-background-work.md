# SPEC 2. 같은 DM의 동시 실행·방향 변경·취소

수정일: 2026-09-09. 코드 확인 기준: `c37f387b`.
이 문서는 이전의 ‘긴 작업 위임’ SPEC을 대체한다. 새 백그라운드 작업 시스템은 만들지 않는다.

## 목표

같은 DM에서 독립적인 작업은 동시에 실행하고, 기존 작업의 수정·취소는 해당 실행에 전달한다.
긴 작업이 실행 중이어도 짧은 질문에 답하고 제어 요청을 처리할 수 있어야 한다.

> 사용자: 메시지 구조를 C로 바꿔줘.
> Agent: C로 바꾸고 있습니다.
> 사용자: 그냥 D로 바꿔줘.
> Agent: D로 변경하겠습니다.

C 작업을 별도로 계속 돌리면서 D 작업을 새로 시작하지 않는다. 기존 작업의 문맥과 실제 변경 사항을
이어받아 D로 방향을 바꾼다. “방금 하라고 한 거 취소해”도 같은 대상 작업에 전달한다.

동시 실행 예:

> 사용자: 메시지 구조를 C로 바꿔줘.
> Agent: C로 바꾸고 있습니다.
> 사용자: 별도로 최근 오류 로그도 조사해줘.
> Agent: 오류 로그 조사도 시작하겠습니다.
> 사용자: 구조 변경은 D로 바꾸고, 로그 조사는 계속해줘.

구조 변경과 로그 조사는 별개 작업이다. D 요청은 구조 변경 작업만 steering하고 로그 조사는 계속한다.

## 현재 동작과 실제 차이

- 메시지에 reply job이 생기더라도 각 메시지가 독립 Worker에서 동시에 실행되는 것은 아니다.
  `worker/src/channels.ts`의 claim은 같은 session에 유효한 running job이 있으면 다른 job을 기다리게 한다.
  Worker 실행 루프는 이미 reply 작업을 `activeSlotCount`에서 제외하고, 일반 작업 슬롯이 가득 차면
  `repliesOnly`로 계속 claim한다. 같은 DM의 session 공유와 Worker 측 `serialKey`가 별도의 직렬화 지점이다.
- `worker/src/dm-reply-steer.ts`는 일반 DM의 후속 입력을 마지막 입력 이후 30초 안에서 기존 job에 합친다.
  `steer_revision`, `applied_steer_revision`, 흡수된 입력 참조가 이미 있다.
- 실행 Worker는 provider가 멈춘 뒤 `AcknowledgeChannelReplySteer`를 호출한다. 같은 job을 다시 claim하고
  저장된 provider conversation으로 이어가는 경로가 이미 있다.
- `worker/src/dm-reply-stop.ts`는 원본 메시지에 대한 명확한 전체 문자열 명령을 처리한다.
  현재 “방금 하라고 한 거 취소해” 같은 일반 DM 후속 표현까지 처리하지는 않는다.

이번 범위는 같은 DM 안에서도 독립 작업에 별도 실행 session을 부여하고, 기존 steering을 장시간 작업에도
연결하는 것이다. 기존 Worker 실행 경로를 사용하되 DM 실행은 Worker 작업 용량 확인과 슬롯 집계에서 제외한다.
별도 실행 서비스를 도입하지 않는다.

## 입력 분류와 대상 선택

| 입력 | 처리 |
| --- | --- |
| “별도로 로그도 조사해줘”처럼 독립적인 요청 | 수신 reply job을 독립 작업으로 확정하고 별도 실행 session 부여 |
| “그냥 D로 바꿔줘”, “그 작업에 테스트도 추가해줘” | 해당 job의 입력 revision을 올려 steering |
| “방금 시킨 작업 취소해” | 해당 job만 취소 |
| “어디까지 됐어?”, 짧은 별도 질문 | 대화 응답만 생성. 작업 목표와 실행은 유지 |
| 대상이나 새 작업 여부가 불명확한 요청 | 짧게 확인. 임의로 시작·수정·취소하지 않음 |

실행 중 작업이 하나라는 이유로 모든 입력을 그 작업에 합치지 않는다. 반대로 메시지가 새로 왔다는 이유로
무조건 새 실행을 만들지 않는다. 기존 30초 자동 합치기도 분류 결과에 따라 적용한다.

대상 선택은 원본/진행 메시지에 대한 답장을 우선한다. public batch는 원본 reply job 참조로 연결한다.
답장 없이 “그냥 D로”처럼 기존 작업을 가리키고 후보가 하나면 그 작업을 선택한다. 여러 개면 명시된
작업 내용과 최근 대화를 사용하고, 둘 이상이 가능하면 확인한다. “방금 시킨 작업”은 가장 최근 사용자 요청에
연결된 작업이며, 이미 끝났다고 다른 실행 중 작업을 대신 선택하지 않는다.

명시적인 작업 참조와 전체 취소 명령은 서버에서 바로 처리한다. 의미 판단이 필요한 입력은 기존 DM Agent의
새 메시지 처리 첫 단계에서 결정한다. 제한된 작업 목록(ID·원본 요청·상태·최근 진행 요약)과 현재 입력만 주고,
`새 작업 / steering / 취소 / 답변 / 확인` 및 선택한 job ID를 구조화된 결과로 받는다.
별도 분류 모델·항상 켜진 관리자 Agent·새 라우팅 서비스를 만들지 않는다. 이 판단이 필요한 경우의
짧은 모델 호출 비용은 허용하며, 실제 작업 도구는 라우팅이 확정된 뒤에만 실행한다.

서버가 권한과 대상의 최신 상태를 다시 검사한 뒤 입력의 처리 결과·target job ID를 고정한다.
재시도는 같은 결정을 사용하고, 매번 더 최근 작업을 다시 선택하지 않는다. 라우팅 대기 중 생성된 incoming
reply job을 기존 job의 입력으로 흡수했다면 독립 실행으로도 claim되지 않도록 원자적으로 확정한다.
대상 후보는 같은 조직·DM·Agent와 사용자 접근 권한 안에서만 찾는다.

## 최소 동시 실행 범위

- DM 실행은 Worker의 작업 용량과 무관하게 배정·claim·실행한다. Worker 작업 슬롯이 모두 사용 중이어도
  독립 DM 요청을 용량 때문에 대기시키지 않는다. DM 실행 수는 Worker 작업 슬롯 사용량에 포함하지 않는다.
- DM당 고정 동시 실행 상한이나 장기 작업·짧은 입력 전용 슬롯 수를 두지 않는다. 단일 Worker에서도
  독립 작업은 서로 다른 Briar session과 작업 디렉터리에서 동시에 실행한다. 질문·steering·취소는 장기 작업의 완료를 기다리지 않는다.
- 실행 가능한 Worker의 연결·권한은 필요하다. Worker 부재나 실제 provider 오류는 기존 대기·실패·재시도 규칙으로 처리한다.
  Worker 용량 설정을 DM 실행 제한으로 다시 적용하지 않는다.
- 새 독립 작업마다 기존 session 구조에 작업별 실행 식별자를 사용한다. 같은 DM이라는 이유로 session을 공유하지 않는다.
  같은 작업의 steering·재시도만 그 Briar session을 이어받는다. 실행할 때마다 새 provider turn을 시작한다.
- 현재 session 단위 동시 claim 방지는 유지한다. DM 전체를 직렬화하던 session 공유를 작업 단위로 바꾼다.
  화면에서는 기존 DM에 계속 표시하고 작업을 새 채널이나 스레드로 강제로 옮기지 않는다.
- 파일을 수정하는 작업은 기존 작업 디렉터리 격리 방식을 사용한다. 같은 checkout을 여러 실행이 동시에 수정하지 않는다.
  동일 저장소라도 격리할 수 있으면 병렬 작업하고, 같은 배포 대상 등 격리할 수 없는 쓰기는 기존 잠금으로 직렬화한다.
  범용 자원 잠금 시스템은 만들지 않는다. 격리·충돌 방지 수단이 없으면 해당 쓰기는 대기시킨다.
- 결과는 완료 순서대로 게시할 수 있다. “구조 변경 결과”, “로그 조사 결과”처럼 어느 작업의 결과인지 알린다.
  작업마다 기존 public batch 순서·중복 방지를 유지한다. 다른 작업의 완료 때문에 현재 작업을 완료 처리하지 않는다.

## 방향 변경: C → D

1. 서버가 후속 메시지를 기존 job에 연결하고 입력 revision을 올린다. 독립 D 실행을 함께 enqueue하지 않는다.
   새 작업/질문으로 분류된 메시지는 흡수하지 않는다. 기존 30초 묶음 처리와 이 경로가 같은 메시지를 두 번 연결하지 않게 한다.
2. 기존 lease/입력 revision 확인 경로로 실행 Worker가 새 입력을 감지한다. 장시간 도구 실행 중에도
   확인할 수 있어야 한다. Worker가 최종 답변을 낼 때까지 입력 전달을 미루지 않는다.
3. Worker가 현재 provider 실행과 관리 중인 도구 프로세스의 중단을 확인한 뒤 steering을 acknowledge한다.
   중단 전에는 재실행을 시작하지 않는다. 프로세스를 즉시 멈출 수 없다면 적용 대기 상태로 남긴다.
4. 같은 작업 ID와 작업 디렉터리, Briar가 저장한 실행 기록을 유지하고 새 claim의 새 provider turn으로 이어간다.
   기존 Worker 배정을 우선한다. Worker가 끊기면 기존 lease 만료·복구 규칙을 따르며, 필요한 문맥이나
   작업 디렉터리를 복구할 수 없으면 실패를 알린다. 다른 Worker가 원래 C 지시부터 다시 실행하지 않는다.
5. Agent는 원래 요청, 이미 수행한 작업, 새 사용자 입력을 함께 읽고 D를 적용한다.
   C 변경이 일부 적용됐다면 그 상태에서 필요한 부분만 수정한다. 관련 없는 사용자 변경을 되돌리지 않는다.

상태 조회는 현재 기록으로 답하고 실행을 중단하지 않는다. 짧은 별도 질문도 독립된 대화 응답으로 처리한다.
작업 방향을 바꾸는 입력만 해당 실행에 전달한다. 변경 대상이 아닌 다른 작업은 계속 실행한다.

“C 대신 D”, 이어서 “D 대신 E”가 오면 수신 순서대로 보존하고 최신 요구까지 반영한다.
전달 접수와 실제 적용을 구분한다. Worker가 입력을 읽기 전에는 변경 완료라고 말하지 않는다.

## 취소

- 원본 답장과 “방금 하라고 한 거 취소해” 같은 명확한 전체 취소 요청을 지원한다.
  “취소라는 단어를 설명해줘”, 인용문, 조건부 문장을 단어 포함 여부만 보고 취소하지 않는다.
- 서버는 대상 job에 취소를 기록하고 기존 claim과 메시지 게시 권한을 무효화한다.
  대기 작업은 시작하지 못하게 하고, 실행 중인 Worker에는 기존 abort 경로로 중단을 전달한다.
- 실행 중에는 먼저 “중단을 요청했습니다”라고 안내한다. Worker의 provider/관리 프로세스 중단 확인 후
  “중단했습니다”로 알린다. lease 만료나 DB 상태 변경만으로 외부 실행까지 중단됐다고 간주하지 않는다.
- Worker가 응답하지 않으면 중단 확인을 기다린다고 표시한다. 취소된 job을 재claim하지 않는다.
- 이미 끝난 변경·게시·배포를 자동으로 되돌리지 않는다. 완료된 부분이 있으면 알려준다.
  되돌리기는 별도 사용자 요청으로 처리한다.

## 저장·경합·구현 범위

- 기존 reply job, 입력 메시지, superseded 관계, revision, claim token, session을 재사용한다.
  `briar_dm_background_tasks` 테이블이나 새 위임 프로토콜은 추가하지 않는다. 작업별 session과 동시 claim을 기존 실행 루프에 연결한다.
- 서버 배정·claim과 Worker 실행 루프 모두에서 DM을 작업 용량 확인·집계에서 제외한다.
  DM 실행 때문에 일반 작업의 사용 슬롯이 늘거나, 일반 작업이 가득 차서 DM 처리가 멈추지 않게 한다.
- 원본 답장과 public batch에서 job을 찾는 작은 resolver를 공통으로 사용한다.
  입력 분류 결과에 따라 새 작업·기존 job 입력·취소·대화 응답 중 하나로 연결한다.
- 수정/취소 접수와 입력 연결·revision 변경은 원자적으로 처리한다. 기존 메시지 요청 고유 키로 재전송을 흡수한다.
- 오래된 claim은 중간 메시지·final batch·완료를 게시할 수 없어야 한다. 이미 게시된 C 진행 메시지는
  삭제하지 않으며, 이후 D로 바뀐 사실을 알려준다. 기존 게시 receipt를 재생성하지 않는다.
- 완료와 수정이 경합하면 DB에서 먼저 확정된 순서를 따른다. 수정이 먼저면 C 완료를 막고,
  완료가 먼저면 그 결과를 보존한 채 D를 새 후속 요청으로 처리한다.
- 취소 접수 뒤 늦은 steering acknowledge나 완료가 작업을 다시 활성화하지 못하게 한다.
- 작업별 session 식별, 입력 라우팅 receipt, 중단 확인에 기존 필드가 부족한 경우에만 nullable 필드·필요 인덱스 또는 기존 RPC의 최소 필드를 추가한다.
  기존 enum의 CHECK를 넓히려고 테이블을 재구축하지 않는다. migration 없이 가능한 경로를 우선한다.

수정 위치: `worker/src/dm-reply-steer.ts`, `dm-reply-stop.ts`, 메시지 접수·claim·완료를 담당하는
`channels.ts`, `channel-reply-claim-routes.ts`, `worker-reply-completion-application.ts`,
`dm-public-message-repository.ts`, 실행 측 `src-cli/worker.ts`, `worker-commands.ts`, `reply-execution.ts` 및 Worker queue contract.
기존 명령 갱신 주기가 부족할 때만 wake/poll 전달을 보완한다. 과거 메시지 backfill이나 모든 DM의 주기적 스캔은 없다.

## 기능별 구현 방식

이 절은 구현 계획이다. 기존 경로와 새로 추가할 동작을 구분한다. 아래 코드 경로는 `apps/briar/` 기준이다.

### 실행 위치와 메시지 접수

Cloudflare API 서버가 메시지·job·session을 저장하고 배정한다. 연결된 컴퓨터의 Briar Worker가 job을 받아
`src-cli/reply-execution.ts`의 `runClaimedChannelReply()`에서 `runtime.runProviderTurn()`으로 AI provider를 호출한다.
DM Agent는 이 실행에 사용하는 Agent 설정이며, 항상 켜져 있는 별도 관리자 프로세스가 아니다.

`worker/src/channels.ts`의 메시지 접수에서 incoming reply job을 만든다. 분류가 필요한 입력에는
작업별 임시 session과 미확정 라우팅 상태를 부여한다. 기존 장기 작업의 session에 넣지 않아야
서버의 session claim 잠금과 Worker의 `serialKey` 뒤에서 분류 자체가 기다리는 문제가 없다.
미확정 job은 분류 단계만 실행할 수 있으며, 제품 변경 도구 실행은 서버가 라우팅을 확정한 뒤 허용한다.

### steering과 독립 요청 분류

1. 서버 resolver가 원본 메시지·public batch에서 대상 job 참조를 찾는다.
   답장은 대상을 정하는 근거다. 답장했다는 이유만으로 steering으로 확정하지 않는다.
   정확한 전체 취소 명령과 유효한 대상이 함께 있으면 기존 `dm-reply-stop.ts`로 바로 연결한다.
2. 의미 판단이 필요한 incoming job은 Worker에서 같은 DM Agent 설정으로 별도 provider turn을 실행한다.
   기존 작업의 conversation ID를 재사용하지 않는다. 분류 호출에는 Briar 작업 변경·메시지 게시 도구 권한을 제공하지 않는다. 어댑터에서 도구 사용이 관찰되면 결과를 폐기한다.
3. 입력은 새 메시지, 최근 DM 문맥, 접근 가능한 작업의 ID·원본 요청·상태·최근 진행 요약이다.
   명시 답장의 대상은 반드시 포함한다. 후보 목록을 잘랐다면 누락 여부를 표시하고, 후보가 하나라는 이유만으로 단정하지 않는다.
4. 출력 schema는 `action: new | steer | cancel | answer | clarify`, `targetJobId`,
   필요한 답변 또는 확인 질문으로 한정한다. `steer`와 `cancel`은 대상 ID가 필수다.
   짧은 질문에 답하려면 실제 조사가 필요한 경우 `new`로 처리한다.
5. Worker는 기존 Worker 인증·claim token을 사용하는 라우팅 확정 RPC로 결과를 제출한다.
   서버는 같은 조직·DM·Agent, 사용자 권한, incoming claim, 대상의 최신 상태를 검증한다.
   모델이 반환한 ID나 동작을 검증 없이 실행하지 않는다.

`worker/src/dm-reply-steer.ts`의 수신 시점 30초 조건으로 대상을 자동 선택하는 경로를 위 결정 이후로 옮긴다.
확정된 steering 입력만 기존 입력 병합에 연결한다. 독립 요청은 30초 안에도 흡수하지 않는다.

### 라우팅 저장과 재시도

새 작업 테이블 없이 기존 incoming reply job에 라우팅 결정과 대상 참조를 저장한다.
최소 추가 필드 후보는 nullable `routing_action`, `routing_target_job_id`다. 기존 queued/running 상태와
claim token을 사용하므로 분류 전용 status를 추가하려고 기존 CHECK를 변경하지 않는다.
분류 대상 일반 DM과 기존 job을 구분하는 초기 표시는 구현 시 기존 메타데이터 또는 nullable 버전 필드로 둔다.
과거 job의 null 값을 새 분류 대기로 해석하지 않는다.

라우팅 확정은 미확정 여부와 유효 claim을 조건으로 한 D1 transaction/batch에서 처리한다.
결정 저장, 입력 흡수, 대상 revision 변경, incoming 완료가 함께 성공해야 한다.
동일 RPC 재전송에는 저장된 결정을 반환한다. 모델 출력 전에 실패하면 분류를 재시도할 수 있지만,
결정이 저장된 뒤에는 다시 분류하거나 다른 대상으로 바꾸지 않는다.

서로 다른 후속 입력은 대상별 서버 접수 순서로 적용한다. 먼저 온 입력의 분류가 끝나지 않았다면
뒤 입력으로 같은 대상의 목표를 먼저 덮지 않는다. 이 대기는 대상 변경 확정에만 적용하고 독립 작업 실행을 막지 않는다.
완료된 대상에 대한 수정은 기존 완료 결과를 보존한 새 후속 작업으로 확정한다.
대상을 확인할 수 없거나 권한이 달라졌으면 다른 작업을 대신 고르지 않는다.

### 독립 작업과 짧은 답변

`new`이면 incoming job과 임시 session을 해당 작업의 실행 ID로 확정하고 실제 작업을 시작한다.
분류용 conversation은 작업 conversation으로 재사용하지 않는다. 실행 프롬프트에는 원본 요청과
확정된 라우팅, 필요한 DM 문맥을 넣는다. 작업 재시도와 steering도 provider conversation 재개 기능을 사용하지 않는다. 원본·변경 요청, 보존된 파일과 Briar 실행 기록으로 새 turn을 시작한다.

`answer`와 `clarify`는 incoming job의 기존 public batch 게시·완료 경로로 한 번 회신하고 종료한다.
상태 답변은 서버가 제공한 작업 상태를 근거로 하며, 진행 중인 작업을 멈추거나 revision을 올리지 않는다.
확인 질문에 대한 다음 사용자 답장은 해당 질문과 원래 입력을 함께 읽어 다시 판단한다.

### 같은 Worker의 동시 실행과 용량 제외

`worker/src/channels.ts`와 `channel-reply-claim-routes.ts`에서 같은 session의 중복 claim 방지는 유지한다.
독립 job에 서로 다른 session을 배정하므로 DM 전체를 기다리게 하던 조건에서 벗어난다.
`src-cli/worker.ts`의 `active`와 `activeControllers`는 실행별로 관리하고,
`serialKey`는 계속 작업 session ID를 사용한다. 채널 ID를 직렬화 키로 추가하지 않는다.

이미 있는 `isReplyWork()`, `activeSlotCount`, `repliesOnly` 처리를 재사용한다.
서버 배정과 Worker 실행 양쪽을 점검해 일반 작업 용량으로 DM을 차단하는 조건만 제거한다.
일반 작업의 동시 실행 설정은 유지하고 DM용 고정 상한은 추가하지 않는다.
독립 작업의 파일 변경은 기존 격리 디렉터리에서 실행한다. steering은 원래 작업 디렉터리를 유지한다.

### 기존 작업의 방향 변경

라우팅 RPC가 `targetJobId`를 받아 `dmReplySteerStatements()`의 입력 연결 동작을 수행하도록 바꾼다.
대상을 session과 시간창으로 다시 검색하지 않는다. incoming 메시지의 원문을 대상 입력에 보존하고
`steer_revision`을 올린 뒤 incoming job을 흡수 완료한다.

실행 측은 기존 명령 확인·lease 갱신에서 revision 차이를 감지하고 해당 실행의 abort controller만 중단한다.
`src-cli/worker-commands.ts`의 중단 후 acknowledge 경로와 `acknowledgeDmReplySteer()`를 재사용한다.
provider와 관리 중인 도구 프로세스가 멈춘 뒤 대상 job을 queued로 돌린다.
새 claim은 같은 Briar session·작업 디렉터리·실행 기록과 미적용 입력을 읽고 새 provider turn을 시작한다.
중단 확인 전에는 다음 provider 실행을 시작하거나 변경 적용 완료를 게시하지 않는다.

### 특정 작업 취소

`dm-reply-stop.ts`의 취소 처리를 검증된 target job에 적용한다. 같은 DM의 다른 job은 갱신하지 않는다.
대기 job은 claim을 막고, 실행 job은 해당 실행에만 중단 명령을 보낸다.
Worker는 provider와 관리 프로세스 중단을 확인한 뒤 기존 명령 acknowledge 경로로 보고한다.
서버는 취소 접수와 중단 확인을 구분해 기록한다. 기존 명령 receipt로 확인 상태를 표현할 수 없을 때만 최소 필드를 추가한다.

취소 접수 시 기존 claim의 일반 게시·완료 권한을 막되, 그 실행이 중단 확인을 제출할 수 있는 인증 경로는 유지한다.
확인 응답은 job·실행·명령 ID를 검증한다. 이전 실행의 응답으로 새 실행을 중단 완료 처리하지 않는다.
연결이 끊기면 중단 확인 대기로 남기고 외부 프로세스까지 종료됐다고 표시하지 않는다.

### 결과 게시와 검증

`dm-public-message-repository.ts`와 `worker-reply-completion-application.ts`에서 기존 claim·revision 검증을 유지한다.
각 public batch를 원본 job에 연결하고, 취소되거나 steering으로 교체된 실행의 늦은 게시·완료를 거부한다.
사용자에게 보여 줄 접수·중단 확인도 기존 게시 receipt로 중복을 막는다.

입력 분류는 독립 요청·수정·취소·질문·모호한 참조 예제로 검증한다.
D1 통합 테스트에서는 라우팅 중복 제출, 같은 대상에 대한 역순 분류 완료, 취소/완료 경합을 확인한다.
Worker 테스트에서는 일반 슬롯이 가득 찬 상태와 같은 DM의 세 개 독립 실행을 확인한다.
실제 provider 검증에서는 실행 시간이 겹치는 증거와 특정 실행만 변경·중단된 결과를 남긴다.

## 완료 기준

- 같은 DM에서 구조 변경과 독립 로그 조사가 실제로 시간상 겹쳐 실행된다. 둘 다 끝나기 전에 짧은 질문에 답한다.
  큐에 두 개가 생긴 것만으로 동시 실행을 통과 처리하지 않는다. 단일 Worker·별도 provider session으로도 확인한다.
- 두 작업 실행 중 구조 변경만 C → D로 steering하고 로그 조사는 계속한다. 로그 조사만 취소하는 반대 조합도 확인한다.
- Worker의 일반 작업 슬롯이 모두 사용 중이어도 DM 작업이 시작되고, DM 실행이 일반 작업 슬롯 집계를 바꾸지 않는다.
  세 번째 독립 DM 작업도 고정 상한 때문에 대기하지 않으며 질문·취소·steering은 계속 처리된다.
  새 입력 중복 전송으로 실행이 추가 생성되지 않는다.
- 같은 작업의 session 중복 실행, 작업 디렉터리 충돌, 다른 작업 결과의 잘못된 귀속이 없다.

- 실제 Worker에서 C 작업을 시작하고 30초 이상 지난 뒤 “그냥 D로 바꿔줘”를 보낸다.
  같은 job·작업 디렉터리에서 이어지고, C와 D가 동시에 실행되지 않으며 최종 결과는 D다.
- 일부 C 변경 후 D 입력을 주어 실제 변경 상태를 이어받는지 확인한다. 완료한 외부 동작을 재실행하지 않는다.
- C → D → E, 중복 입력 전달, provider 중단 지연, Worker 재시작에서 최신 요구가 유실되지 않는다.
- 원본/진행 메시지 답장과 답장 없는 “방금 하라고 한 거 취소해”를 확인한다.
  취소 후 도구 실행·공개 메시지·늦은 완료가 계속되지 않고, 확인 전에는 중단 완료로 표시하지 않는다.
- 짧은 상태 질문이나 “취소라는 단어를 설명해줘”가 작업 취소·목표 교체를 일으키지 않는다.
- 여러 대상의 모호한 요청, 이미 끝난 작업, 다른 DM 작업에는 잘못 전달하지 않는다.
- 기존 30초 묶음 테스트를 입력 분류 기준으로 갱신한다. 독립 요청은 30초 안에도 병렬 실행되고, 수정은 30초 이후에도 steering된다.
  명시 중단·재시도와 revision/완료 경합을 실제 D1에서 검증한다.
  실제 provider로 C → D와 취소를 각각 검증한 뒤 지원 범위를 기록한다.

## 제외

새 백그라운드 작업 큐, 자동 작업 분해·위임, 모든 provider의 실시간 토큰 중 steering,
자동 rollback, 프로젝트 위임/Agent 간 hop을 넘어선 취소 전파, 새 제어 화면, 별도 의도 분류 엔진.
초기 대상은 현재 steering이 지원하는 일반 1인·1Agent DM reply다. Skill·위임 작업까지 지원한다고 표시하지 않는다.

## 구현 범위

현재 등록된 모든 provider에 같은 실행 규칙을 적용한다. Worker가 설치된 provider와 공통 호스트
프로세스 관리 기능을 광고하며, 특정 provider의 중단·steering·대화 재개 API를 요구하지 않는다.
지원 호스트는 macOS/Linux다. 미설치 provider와 구버전 Worker는 기존 경로를 유지하고,
설치된 provider의 일시적인 오프라인·준비 지연에는 입력을 큐에 보관한다.

분류는 선택된 Agent의 기존 실행 어댑터를 읽기 전용 격리 환경에서 호출한다. 실행 세션·첨부·Skill·
Briar 도구 권한을 제공하지 않고, 정규화된 도구 실행이나 승인 요청이 관찰되면 중단하고 분류 결과를
채택하지 않는다. 외부 CLI 내부에서 도구가 제거되었다고 가정하지 않는다. 특정 provider의 도구 제거
API나 다른 provider로의 우회 호출은 사용하지 않는다.

중단은 Briar 부모 프로세스가 실행별 runner와 자식 프로세스의 신원을 추적해서 처리한다.
대상 프로세스를 정지시켜 추가 실행을 막고 종료한 뒤, 사라졌는지 확인해야 acknowledge한다.
추적·종료 확인에 실패하면 기존 stop-unconfirmed fence를 유지해 후속 실행을 막는다.

steering·재시도는 provider conversation ID를 재개하지 않는다. 같은 작업 디렉터리와 현재 입력,
최대 48,000자의 최근 정규화 실행 기록을 새 turn에 제공한다. 기록은 불완전할 수 있으므로
실제 파일과 외부 작업 상태를 확인하고, 이미 완료한 외부 효과를 반복하지 않도록 지시한다.
provider의 실시간 토큰 steering·네이티브 checkpoint는 사용하지 않는다.

예약·DM 게시 도구는 모든 provider에서 같은 Briar 로컬 명령을 호출한다. 명령은 작업 폴더의 요청·응답 파일을 사용한다. Briar 부모 프로세스만 실행별 private
capability와 기존 인증 socket으로 서버에 요청한다. provider의 MCP 지원 여부나 MCP 승인 설정,
Unix socket 연결 권한 예외에 의존하지 않는다. 서버의 job·revision·DM 권한 검사는 그대로 적용한다.


### 공통 provider 경로 검증 (2026-09-09)

실제 Codex Worker loop에서 A/B 동시 작업, 짧은 질문의 선행 답변, C 작업 중 D 입력,
작업 폴더와 기록을 보존한 새 provider turn, B만 취소하는 흐름을 10개 항목으로 확인했다.
