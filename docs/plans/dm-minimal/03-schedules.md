# SPEC 3. 나중에 이어서 확인하고 일정 간격으로 실행하기

실행 기반: 기존 DM reply 생성·실행·회신 경로. 실행 중인 작업의 제어는 [SPEC 2](02-background-work.md)에 따른다.
SPEC 2 개정에 맞춰 연결점만 수정했다. 별도 백그라운드 작업 테이블을 전제하지 않는다.

## 목표

“두 시간 뒤에 다시 확인해줘”, “한 시간마다 상태를 확인해줘”를 실제 예약으로 저장한다.
시간이 되면 Worker가 실행하고, 결과는 원래 DM Agent가 정리해 답한다. 앱을 닫아도 예약은 유지된다.

## 현재 있는 것

프로젝트 Agent용 예약은 `worker/src/team-agent-schedule-repository.ts`와 application에 있다.
반복 주기 계산·claim·실행 이력을 이미 다룬다. 하지만 프로젝트에 묶인 예약을 일반 DM에 쓰기 위해
가짜 프로젝트를 만들지는 않는다. `worker/src/scheduled-task.ts`의 기존 분 단위 tick을 사용한다.

## 지원 범위

| 요청 | 저장할 형태 |
| --- | --- |
| “두 시간 뒤에 확인” | 한 번 실행할 UTC 시각 |
| “매시간 확인” | 최초 실행 시각 + 고정 간격 |
| “예약 보여줘” | 이 DM의 예약과 다음 실행 시각 |
| “그 예약 취소해줘” | 지정 예약 비활성화 |

반복은 분/시간/일의 고정 간격만 지원하고 최소 간격은 5분이다. “매일”은 24시간 간격이라는 점을
확인 문구에 적는다. 달력 기준 평일·매월·복잡한 cron은 제외한다.
상대 시간은 서버 접수 시각에서 계산한다. 절대 시간은 확인된 사용자 시간대를 사용하며,
시간대나 대상 작업이 불명확할 때만 묻는다. 예약 저장 후 사용자의 시간대로 다음 실행 시각을 알려준다.

## 최소 구현

새 `briar_dm_schedules` 테이블 하나를 추가한다.

- 예약 ID와 생성 요청 고유 키, 조직·DM·소유자·Agent·원본 메시지 참조.
- 실행할 지시와 선택적인 이전 작업 참조.
- 다음 실행 시각, 반복 간격(없으면 일회성), 표시용 시간대, 활성 여부, 변경 revision.
- 현재 연결된 작업 ID와 생성/수정 시각.

Agent 도구는 생성·목록·취소 세 개로 한정한다. 시간 변경은 취소 후 새 예약 생성으로 처리한다.
예약 전용 실행 이력 테이블, cron 서비스, 달력 화면은 만들지 않는다.

기존 분 단위 tick에 다음 처리를 추가한다.

1. `(enabled, next_run_at)` 인덱스로 기한이 된 예약만 최대 20개 읽는다.
2. 예약 revision과 다음 시각을 조건으로, 기존 DM reply job 생성과 예약 갱신을 같은 D1 transaction/batch에서 처리한다.
   예약 ID + 예정 시각을 작업 생성 고유 키로 써서 tick 중복 호출로 같은 회차가 늘어나지 않게 한다.
3. 일회성은 작업을 성공적으로 큐에 넣으면 비활성화한다. 반복은 기준 시각의 간격을 유지하며
   현재 이후의 가장 가까운 시각으로 이동한다. 오래 놓친 회차를 한꺼번에 실행하지 않는다.
4. 실행·재시도·회신은 기존 DM 경로를 사용하고, 실행 중 변경·취소는 2번 SPEC을 따른다. tick에서 모델을 호출하지 않는다.

“이어서”는 저장한 지시·직전 결과·산출물 참조를 읽고 새 실행을 시작한다는 뜻이다.
기존 실행기가 지원하는 checkpoint는 재사용할 수 있지만, 몇 시간 전 프로세스를 그대로 되살리는 기능은 아니다.
이미 수행한 외부 작업을 다시 하라는 지시로 바꾸지 않는다.

## 누락·중복·취소 규칙

- 서버 저장 확인 전에는 예약했다고 말하지 않는다. 실패하면 이유를 짧게 알린다.
- Worker가 없으면 실행 작업은 대기로 남는다. 같은 예약의 대기/실행 작업을 더 만들지 않는다.
- 예약 회차도 독립된 작업 session을 사용하며, SPEC 2에 따라 Worker 작업 용량 확인·슬롯 집계에서 제외한다.
  다른 작업이 실행 중이라는 이유로 예약 실행을 대기시키지 않는다. 단, 같은 예약의 이전 회차가 대기·실행 중이면 중첩 실행하지 않는다.
  Worker 부재 등으로 밀린 반복 회차는 횟수만큼 쌓지 않고 한 번으로 합친 뒤 다음 미래 시각을 계산한다.
  다음 실행이 지연될 수 있음을 접수 문구에 명시한다.
- 예약 취소와 tick이 경합하면 revision으로 새 작업 생성을 막는다. 이미 생성된 작업에도 취소를 전달한다.
  실행이 시작됐다면 2번 SPEC의 중단 확인 규칙을 따른다. 과거 외부 효과를 되돌렸다고 말하지 않는다.
- 예약 수정·취소 후 오래된 완료가 새 예약을 다시 켜거나 다음 실행 시각을 덮지 못한다.
- 실행 실패는 한 번 보고하고 기존 실행 재시도 규칙을 따른다. 일회성 예약을 다시 활성화하지 않는다.
  반복 예약은 다음 주기에 계속 실행하며 사용자가 취소할 수 있다.
- DM 삭제, 권한 회수, 대상 Agent 제거 시 실행·회신을 중지한다. 예약은 새로운 실행 권한을 부여하지 않는다.
- 정상 실행마다 결과를 회신한다. “변경이 있을 때만 알림” 같은 조건별 보고 정책은 이번 범위에서 제외한다.

## 비용과 완료 기준

기존 DB를 재작성하지 않고 빈 예약 테이블과 기한 조회 인덱스만 추가한다.
tick은 기한 조회와 필요한 상태 변화만 수행한다. 모든 예약 내용을 읽거나 매분 모델에게 판단시키지 않는다.
운영 적용 전 예상 예약 수에 따른 tick 읽기·실행당 쓰기·모델 호출 수를 기록한다.

검증:

- 실제 Worker로 짧은 일회성 예약 하나를 실행해 앱을 닫은 상태에서도 원래 Agent의 결과 회신을 받는다.
- 시계를 제어한 통합 테스트로 두 번의 반복, 지연 tick, 중복 tick에서 회차당 작업 하나만 생성됨을 확인한다.
- 장시간 Worker 부재·기존 작업 실행 중에도 예약 작업이 무한 누적되지 않는다.
- 취소/tick 경합, 완료 응답 재시도, DM 권한 회수에서 중복 실행·잘못된 회신이 없다.
- 상대 시간과 확인된 시간대의 절대 시간을 검증한다. 초 단위 정시 실행을 보장하지 않는다.

## 제외

범용 cron/RRULE, 영업일·공휴일 달력, 작업 의존성 그래프, 조건 충족 감시 엔진,
별도 예약 관리 화면, 자동 비용 최적화, 같은 예약 회차의 중첩 실행, 운영 사용자 대상 시험 예약.

## 구현 기록 · 2026-09-09

구현은 `apps/briar/worker/src/dm-schedules.ts`의 생성·목록·취소와 `runDueDmSchedules()`에 있다.
기존 분 단위 tick이 최대 20개의 기한 인덱스 항목을 읽고, 동일 D1 batch에서 Briar 명의의 회차 메시지,
독립 session, 기존 DM reply job, 예약 revision/다음 시각을 확정한다. 예약 ID와 예정 시각에서
결정적인 UUID를 만들어 기존 메시지·job의 고유 제약을 유지한다. 모델은 tick에서 호출하지 않는다.

migration `0217_dm_schedules.sql`은 빈 예약 테이블과 인덱스, 기존 reply job의 nullable
`dm_schedule_id`만 추가한다. 과거 행 backfill, 테이블 재구축, 운영 DB 변경은 하지 않았다.
해당 참조는 예약이 삭제되어도 남아, 원래 예약이 사라진 작업이 실행 권한을 되찾지 못하게 한다.

Agent 도구는 기존 DM publication socket을 통한 `create_dm_schedule`, `list_dm_schedules`,
`cancel_dm_schedule`이다. 조직·DM·소유자·Agent는 입력으로 받지 않고 현재 Worker claim에서 결정한다.
목록은 50개씩 반환하며 잘렸으면 마지막 ID를 cursor로 이어 읽는다. 도구 응답의 지시 요약은
200자로 제한하고 실제 실행 지시는 8,000자까지 보존한다. 상대 시간은 원래 메시지의 서버 접수
시각에서 계산한다. 절대 시간은 명시적으로 확인한 IANA 시간대를 요구한다.

현재 등록된 모든 provider에서 SPEC 2의 공통 실행 경로와 같은 예약 명령을 사용한다.
Briar가 제공하는 명령을 일반 shell/terminal 도구로 호출한다. 명령은 작업 폴더의 요청·응답
파일을 사용하고, Briar 부모 프로세스가 고정된 invocation socket으로 중계한다. private capability와
기존 서버 검증이 생성·조회·취소 권한을 제한한다. 특정 provider의 MCP·스케줄·승인 API는
사용하지 않는다. capability를 광고하지 않는 구버전 Worker는 새 예약을 실행하지 않는다.
원본 메시지 version, DM roster epoch, 조직·프로젝트 접근 권한, Agent provider를 실행·갱신·게시에서
검사한다. 예약 회차에 대한 후속 steering도 기존 SPEC 2의 같은 작업 경로로 전달한다.

이전 결과와 최대 10개의 첨부 참조는 claim 시점에 같은 DM에서 읽는다. 삭제·기억 제외한 결과는
제외하고, 첨부는 기존 인증 다운로드 경로로 전달한다. 이전 프로세스나 provider conversation을
새 회차에서 재사용하지 않는다. Worker 작업 용량 확인과 슬롯 집계에서 제외하는 SPEC 2 동작을 유지한다.

  realtime hub 전달은 stub이었다. 실제 운영 알림·로그인 UI·Linux provider 실험까지 검증했다고 표현하지 않는다.
  운영 예약이나 배포·병합은 실행하지 않았다.

### 비용 기록

격리된 로컬 D1에 반복 예약 하나를 넣고 기존 schema trigger까지 포함해 측정했다.
`rows_read`/`rows_written` 기준이며, 운영 데이터 분포·인덱스·기존 trigger 부하에 따라 달라진다.

| tick 상태 | 새 회차 | 읽은 행 | 쓴 행 |
| --- | ---: | ---: | ---: |
| 첫 기한 도달 | 1 | 75 | 42 |
| 같은 시각 중복 호출 | 0 | 1 | 0 |
| 이전 회차 대기 중 하루 지연 | 0 | 58 | 2 |

첫 기한의 논리적인 변경 대상은 메시지·session·job·예약 네 행이다. 실제 쓰기 수는 기존 trigger와
인덱스 비용까지 포함하므로 네 번의 D1 쓰기라고 추정하면 안 된다. due 조회는 `(enabled, next_run_at)`
인덱스와 `limit 20`을 사용하고 전체 예약이나 과거 메시지를 매분 읽지 않는다.

예를 들어 100개가 매시간 실행되면 겹침·실패가 없을 때 하루 2,400회의 Agent 실행이다.
위 작은 fixture의 비율을 단순 적용하면 회차 처리에서 하루 약 180,000행 읽기와 100,800행 쓰기이며,
빈 tick·claim·lease·최종 게시·실제 작업의 비용은 별도다. tick 자체의 모델 호출은 0회이고,
각 회차는 기존 Agent 실행 한 번으로 시작한다. 도구 사용과 재시도에 따른 내부 모델 호출은 추가될 수 있다.
한꺼번에 몰린 예약은 tick당 20개씩 처리하므로 정시 실행을 보장하지 않는다.
