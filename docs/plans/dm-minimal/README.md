사용자가 정한 세 가지 목표만 구현한다. 과거 12개 SPEC은 이 작업의 선행 조건이 아니다.

| 순서 | SPEC | 사용자에게 생기는 기능 | 신규 저장 구조 상한 |
| --- | --- | --- | --- |
| 1 | [개인화 기억](01-profile.md) | 특징·선호를 기억하고 관련 답변에 참고 | 없음 |
| 2 | [동시 실행·변경·취소](02-background-work.md) | 독립 작업은 병렬 실행하고, 수정·취소는 해당 실행에 전달 | 새 작업 테이블 없음 |
| 3 | [후속 확인·반복 실행](03-schedules.md) | 나중에 한 번 또는 일정 간격으로 작업하고 DM으로 결과 받기 | 예약 테이블 1개. 기존 DM reply 실행 기록 재사용 |

1번은 독립적으로 진행할 수 있다. 3번은 기존 DM reply 실행 경로를 사용하며, 실행 중인 예약 작업의 변경·취소에는 2번을 연결한다.
각 항목을 별도 PR로 검증·배포한다. 하나의 거대한 기능 플래그나 공통 프레임워크를 먼저 만들지 않는다.

공통 경계:

- 기존 기억 권한, Worker 권한, 작업 승인, 메시지 재시도 규칙을 유지한다.
- DM 실행은 Worker 작업 용량 확인·슬롯 집계에서 제외하며, DM당 고정 동시 실행 상한을 두지 않는다. 예약으로 시작한 DM 작업에도 적용한다.
- 과거 DM 전체 재처리, 테이블 재구축, 대량 backfill은 하지 않는다. 새 데이터부터 적용한다.
- 새 테이블은 필요한 단계에서만 추가한다. migration 번호는 구현 당시 main을 기준으로 정한다.
- API 계약은 기존 proto와 생성 절차를 따른다. 새 서버·큐 제품·스케줄러 서비스를 도입하지 않는다.
- UI는 기존 DM과 기억 관리 화면을 사용한다. 새 대시보드·작업 관리 화면·예약 달력은 제외한다.
- 클라이언트 코드가 필요한 변경은 웹·데스크톱·Android·iOS에서 확인한다. 실행 Worker 번들 배포까지 구분해 기록한다.
- 완료 기준은 실제 저장·실행·회신이다. 프롬프트에 지시문이 있다는 것만으로 완료하지 않는다.

이 범위에서 제외: 범용 행동 정책 엔진, 사용자 성격 점수, 조건별 보고 보류, 논리적 대화 턴 재설계,
다중 Agent 협업 그래프, 실행 중 세션 이관, 범용 cron 편집기, 새로운 통합 평가 플랫폼.
